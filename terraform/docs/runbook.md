# Runbook: Bastion / SSM Access Errors

Companion to [`sops.md`](./sops.md) in this folder, which documents the bastion access procedure
itself. This runbook covers what to do when a step in that procedure fails.

Covers errors you may hit connecting to a bastion host, or to a non-local database through one. A
failure in this layer usually *looks* like a credential or key problem, so work down the table in
order rather than jumping to the row that matches your guess.

For errors in the database backup scripts themselves, see
[`../scripts/runbook.md`](../scripts/runbook.md).

| Symptom | Likely Cause | Resolution |
|---|---|---|
| `run-on-bastion` or `copy-to-bastion` produces **no output at all** -- no tunnel message, and nothing on stdout | `BASTION_ID` or `BASTION_SSH_KEY` is unset. Both are validated with `${VAR:?...}` *before* the script prints anything, and that writes to **stderr**, leaving stdout completely empty. Neither is in `.env`, so `BASTION_ID` in particular does not survive opening a new terminal. | `echo "id=$BASTION_ID key=$BASTION_SSH_KEY"`; export whichever is empty and retry. Check stderr, where the real message is. |
| `SessionManagerPlugin is not found` | The AWS CLI shells out to `session-manager-plugin` by name and it isn't on `PATH`. | Run from a `nix develop` shell, which provides it. This is the single most common cause of every other symptom in this table. |
| `scp: Connection refused` or `ssh: connect to host localhost port 2222: Connection refused`, immediately after `Waiting for tunnel to come up...` | The SSM tunnel never opened, so nothing is listening locally. Almost always the missing plugin above -- *not* a bad key. | Check `command -v session-manager-plugin` first. The flake apps now fail with an explicit tunnel message instead of falling through to this, so if you see the bare `Connection refused` you may be on an older checkout. They also check the local port is free before opening the tunnel, and abandon the readiness wait as soon as the SSM session exits, so this class of failure now reports itself in about a second rather than after the full 15-second wait. |
| `An error occurred (TargetNotConnected) when calling the StartSession operation` | The SSM agent on the instance is not registered or has lost its connection. Nothing can be delivered to the host in this state. | `aws ssm describe-instance-information --filters "Key=InstanceIds,Values=$BASTION_ID"` -- if the list is empty or `ConnectionLost`, this is an infrastructure problem, not a client one. There are no SSM VPC endpoints in the Terraform, so agent reachability depends on a NAT path that nothing in this repo asserts. Escalate. |
| `Error: expected length of oauth_token to be in the range (1 - 1000), got` and/or the same for `repository`, on `aws_amplify_app.dailp`, from `tf-plan` | `terraform/website.nix` reads these from `getEnv "OAUTH_TOKEN"` and `getEnv "GIT_REPOSITORY_URL"`. Both live in `.env`, and **`nix run` does not source `.env`** -- only `nix develop` does, via the shellHook's `direnv dotenv`. So a `nix run .#tf-plan` from a shell without them emits `""`, and the Amplify provider rejects a zero-length string. **The quoted `config.tf.json` line number is a generated artifact on disk, not a source location** -- and critically, bare `terraform plan`/`apply` never regenerate it. Only the nix apps do (`cp -f $terraformConfig ./config.tf.json`). So once a `tf-init` has run in an environment missing the variable, the empty value is written to disk and every subsequent bare `terraform` command faithfully re-reads it -- which makes this look like it "persists even after fixing the environment". Note also that `-target` **masks** this error entirely, because Terraform only validates the targeted resource; a targeted plan succeeding does not mean your config is good. | Load the variables and then **regenerate**, in that order: `set -a; . ./.env; set +a` then `nix run --impure .#tf-init`. Re-running bare `terraform plan` alone will not help. Verify with `grep -c '"oauth_token": ""' config.tf.json` -- expect `0`. Confirm with `[ -n "$OAUTH_TOKEN" ] && echo set` before re-running. Note this is the loud version of a wider problem -- the `AWS_SUBNET_*` / `AWS_ZONE_*` variables are *not* in `.env` and fail **silently**, so see the row below and the `-target` guidance in [`sops.md`](./sops.md) before running any local apply. |
| `terraform plan` proposes `~ subnet_ids = [- "subnet-...", + ""]` on `aws_db_subnet_group.sql_database`, or empty availability zones on the database | `AWS_SUBNET_PRIMARY`, `AWS_SUBNET_SECONDARY0`, `AWS_SUBNET_SECONDARY1` and `AWS_ZONE_*` exist only as GitHub secrets -- they are not in `.env`, so they are empty in every local shell and `getEnv` emits `""`. `terraform/main.nix` warns for each. This is the single most dangerous local-apply failure mode, because the damaged resource is one you are not thinking about while working on something else. | **Do not apply.** Export the values (read them off the live resources or the repository secrets), and always `-target` a local apply at the specific resource you mean to change -- see "Never run an untargeted `terraform apply`" in [`sops.md`](./sops.md). If you have already applied and the subnet group is broken, re-run the deploy workflow from CI, which has the secrets, and verify with `aws rds describe-db-subnet-groups --db-subnet-group-name dailp-<stage>-database`. |
| `Error: failed to get shared config profile, <name>`, immediately followed by `Error loading the state: failed to get shared config profile, <name>`, from any `tf-*` app | `AWS_PROFILE` names a profile that is not in `~/.aws/config`. **This is config resolution, not credentials** -- Terraform's S3 backend resolves `AWS_PROFILE` against the shared config before and independently of authentication, so it fails identically whether or not you have valid keys exported. Do not chase it as an expired-token problem (that is the `403 Forbidden` row below, which looks nothing like this). The usual cause is pasting the AWS access-portal label, `PermissionSet-AccountId` -- e.g. `NEU-SystemAdministrator-783177801354` -- which is a display name, not a profile name. `AWS_SDK_LOAD_CONFIG=true` in the environment makes shared-config loading mandatory, so there is no fallback. | `aws configure list-profiles` -- that is the authoritative list. For the dev/uat account the profile is `library-dev`. Then `export AWS_PROFILE=library-dev` and re-run. Confirm with `aws sts get-caller-identity` first; if the SSO token has expired, `aws sso login`. If something in your shell keeps re-setting a bad `AWS_PROFILE`, materialise credentials and drop the reference instead: `eval "$(aws configure export-credentials --format env)"` then `unset AWS_PROFILE`. Note `nix run` does not source `.env` (only `nix develop` does), so the repo's `AWS_PROFILE=library-dev` does not apply to `nix run .#tf-*`. |
| `An error occurred (AccessDeniedException) ... ssm:StartSession` / `ssm:SendCommand` | Your IAM principal lacks the action. `StartSession` and `SendCommand` are separate permissions -- having one does not imply the other. | `aws sts get-caller-identity` to confirm which principal you're using. Only `StartSession` is needed for anything in [`sops.md`](./sops.md); `SendCommand` is not. |
| `An error occurred (403) when calling the StartSession operation: Server authentication failed: <UnauthorizedRequest><message>Forbidden.</message></UnauthorizedRequest>` | Note this is **not** the JSON `AccessDeniedException` shape an IAM denial produces, which makes it tempting to theorise about proxies and WAFs. In practice it was **stale credentials**. `.env` is gitignored and per-machine, so check yours before assuming: it may carry temporary `ASIA...` credentials plus `AWS_SESSION_TOKEN` that the dev shell sources automatically and that expire, though the current committed shape sets only `AWS_DEFAULT_REGION` and `AWS_PROFILE`. Note also that static credential env vars take precedence over `AWS_PROFILE` in the SDK chain, so adding a profile does *not* override expired values still sitting in the environment. | `aws sts get-caller-identity` first -- always, before reasoning about the error text. To switch to an SSO profile you must clear the old values, not just set the new ones: `unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY AWS_SESSION_TOKEN`, then `export AWS_PROFILE=...` and `aws sso login`. For Terraform (`tf-output`, `tf-plan`) also run `eval "$(aws configure export-credentials --format env)"`, since it has no `--profile` flag. |
| `Permission denied (publickey)` | The tunnel is working (you reached sshd) but `BASTION_SSH_KEY` isn't in the bastion's `authorized_keys`, or `BASTION_SSH_USER` is wrong. | Re-run with `ssh -vvv` and read the `Offering public key` / `Authentications that can continue` lines. Confirm the login user is `ec2-user`. If no key you hold works, use the keyless `aws ssm start-session` path in [`sops.md`](./sops.md) to add one. |
| `WARNING: UNPROTECTED PRIVATE KEY FILE!` followed by `This private key will be ignored` | The key file's permissions are too open (e.g. `0644`, typical of a fresh browser download). Reads like a corrupt key, but isn't. | `chmod 600` the key file. Keep keys in `~/.ssh/`, not `~/Downloads`. |
| `Load key "...": error in libcrypto` or `invalid format` | The key content is mangled -- usually a lost trailing newline or lost line breaks from a copy-paste into a secret store. | Re-copy the file verbatim, including the `-----BEGIN`/`-----END` lines. When storing in a secrets manager, verify the consumer re-adds a trailing newline; if it can't, store the key base64-encoded and decode on use. |
| `Local port 2222 is already in use, so the tunnel cannot bind it`, or (on the manual 5432 recipes, or an older checkout) `bind: Address already in use` and a tunnel that appears up but connects to the wrong thing | Local port already bound -- a leftover `session-manager-plugin` from an interrupted run, or a local Postgres on 5432. Worth knowing why the silent version was the dangerous one: the readiness probe only asks whether *something* is listening, so a bind failure used to leave `ssh`/`scp` riding whichever session already owned the port. If that session had passed SSM's idle timeout, `ssh` hung indefinitely with no output -- `ConnectTimeout` only covers the TCP connect, which the local plugin socket answers regardless, `ServerAlive*` only applies once the transport is up, and OpenSSH has no client-side banner timeout. | `lsof -i :2222` / `lsof -i :5432` and kill the stale process. For SSH, override with `BASTION_LOCAL_PORT`. The flake apps now refuse to start on a busy port rather than reusing the stale listener, and they kill the tunnel's whole process group on exit, so they should not be the source of the leftover any more. |
| A step that captures `run-on-bastion` output produces **all** of its expected output -- the tunnel messages, the script's `log_event` lines, `Backup written to ...` -- and then goes silent until `timeout-minutes` kills it. Seen on the Data Backup workflow's `Run database backups on bastion` step, which burned its full 60 minutes this way. | `aws ssm start-session` used to inherit the caller's stdout, and it runs `session-manager-plugin` as a child that inherits the same descriptor. Because the old cleanup killed only the `aws` wrapper, the plugin was orphaned while still holding the write end of the caller's `$( ... )` pipe, so the command substitution never saw EOF. The remote work had already finished; only the capture was stuck. Note that wrapping the call in `timeout` does not help -- the pipe outliving `nix run` is the whole problem. | Fixed at the source: `bastionTunnel` in [`flake.nix`](../../flake.nix) now redirects the tunnel's stdout to stderr and kills its process group on exit. On an older checkout, avoid `$(run-on-bastion ...)` -- redirect stdout to a file and read the file back, which is what the Data Backup workflow does now. |
| `Starting session with SessionId: ...` succeeds, then `Cannot perform start session: listen unix /var/folders/.../nix-shell.XXXXXX/<digits>_session_manager_plugin_mux.sock: bind: invalid argument` | **macOS only, and only for port forwarding.** The plugin binds a Unix-domain multiplexer socket at `$TMPDIR/<digits>_session_manager_plugin_mux.sock` (42-char basename). Darwin caps `sockaddr_un.sun_path` at 104 bytes, 103 usable; `nix develop` sets `TMPDIR` to a ~65-char `/var/folders/.../nix-shell.XXXXXX` path, giving 108, and `bind()` returns `EINVAL`. macOS's bare `TMPDIR` (~48 chars) is short enough, so this appears only inside the dev shell. Note the session itself started -- credentials and permissions are fine. | The flake apps handle this themselves. If you're invoking `aws ssm start-session` directly, prefix it with `TMPDIR=/tmp`. Do **not** chase this as a credentials or IAM problem; a plain `aws ssm start-session` with no `--document-name` will still work, because plain sessions never bind this socket. |
| `psql: could not connect to server` after the tunnel reported ready | The readiness loop broke out on a socket that closed immediately, or `DATABASE_PASSWORD` isn't set. | Confirm `DATABASE_PASSWORD` is exported, then re-run `psql "$DATABASE_URL" -c 'select 1;'` to separate auth from connectivity. See also the `pg_dump failed.` row in [`../scripts/runbook.md`](../scripts/runbook.md). |
| `An error occurred (InvalidInstanceId)` | `BASTION_ID` is empty or points at another stage's instance. | Job-level environment config cannot always resolve stage-conditional values; confirm `echo $BASTION_ID` is non-empty and matches the stage you intend. |
| `upload failed: ... An error occurred (AccessDenied)` from `upload_to_s3.sh` in the Data Backup workflow | **Check which of the two upload steps failed first -- they use different identities.** The `Upload backup bundle to S3` step runs on the runner as the `dailp-deployment` user, which `terraform/media-storage.nix` grants `s3:PutObject` on the whole media bucket, so a denial there is an identity problem. The `Upload database backups to S3 from bastion` step runs as the *bastion instance role*, whose own policy grants only `s3:GetEncryptionConfiguration`; its write access comes from the bucket side instead, via `allow_bastion_backup_writes` in `terraform/media-storage.nix`, and is scoped to `db-backups/*`. | Runner step: `aws sts get-caller-identity` and confirm the ARN is `arn:aws:iam::783177801354:user/dailp-deployment` (dev). If it is something else, the `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` secrets on the `Development` environment are wrong; if it *is* that user, the bucket policy has drifted -- `terraform plan` and escalate. Bastion step: read the **prefix in the failing key** first. Anything outside `db-backups/` is denied by design and wants a new statement in `media-storage.nix`, not troubleshooting. If it *is* under `db-backups/`, the bucket policy has drifted -- `aws s3api get-bucket-policy --bucket dailp-<stage>-media-storage` and check the `AllowBastionDbBackupWrites` statement is present and names the live role ARN, then `terraform plan`. Do not go looking on the role: the grant is deliberately not there. A working SSH key does not imply a working upload. |
| `The backup scripts need bash >= 4.3 for local -n namerefs` from the `Check backup prerequisites on bastion` step | Every script in `./scripts` uses `local -n` namerefs (`create_logfile`, `resolve_pg_target`, `upload_objects`), which bash added in 4.3. Amazon Linux 2 ships bash 4.2; AL2023 ships 5.2. Without this preflight the failure surfaces mid-backup as `local: -n: invalid option`, which names neither the database nor the script that broke. | **First establish which OS you actually reached** -- `run-on-bastion -- '. /etc/os-release; echo $PRETTY_NAME'`. On AL2023 this check cannot legitimately fail, so tripping it means `BASTION_ID` / the stage's `*_EC2_INSTANCE` secret points at an older instance than you think; fix the secret. On Amazon Linux 2 it is a real OS limitation with no fix from the workflow -- there is no bash >= 4.3 in the AL2 repos, and AL2 itself reached end of support on 2026-06-30. The stage needs migrating to AL2023; see "Replacing the bastion AMI" in [`sops.md`](./sops.md). Escalate rather than working around it per-run. |
| `Still on Postgres client major version N after installing` from the `Check backup prerequisites on bastion` step | The package install ran but did not produce a client >= 14, which a Postgres 14 server requires (`pg_dump` refuses to dump a server newer than itself). The preflight branches on the OS, so the cause differs: on AL2023 `dnf install postgresql15` resolved to something unexpected; on Amazon Linux 2 `amazon-linux-extras enable postgresql14` succeeded but the following `yum install postgresql` picked up the base 9.2 package. | On AL2023: `sudo dnf install -y postgresql15` explicitly, and if that is unavailable `dnf search postgresql` to find the current client package name (`postgresql16` on newer releases). On Amazon Linux 2: `sudo amazon-linux-extras list` to see which postgres topic is enabled, then `sudo yum install -y postgresql14` explicitly (some AL2 revisions name the package with the version suffix). Either way confirm with `pg_dump --version` before re-running the workflow -- both `pg_dump` and `psql` must be >= 14, since the two backup scripts use different binaries. |
| `Cannot import non-existent remote object`, or a plan that imports the bastion and then immediately proposes replacing it | [`import.nix`](../import.nix) renders the bastion's import block from the `BASTION_ID` environment variable, sourced from the stage's `*_EC2_INSTANCE` secret. After any out-of-band instance replacement that secret is stale and points at a terminated instance. Terraform skips import blocks for resources already in state, so this usually surfaces only when state is rebuilt -- but the same stale value breaks every workflow that targets SSM by instance id, which is the more common symptom. | Look up the live instance (`describe-instances` filtered on `tag:Name`, as in [`sops.md`](./sops.md)) and update `DEV_EC2_INSTANCE` / `UAT_EC2_INSTANCE` / `EC2_INSTANCE` to match. Do not "fix" it by editing `import.nix`. |
| `terraform plan` proposes **replacing** `module.bastion_host.aws_instance.default[0]` | Something in the config disagrees with the running instance on a ForceNew attribute. In rough order of likelihood: `AWS_SUBNET_BASTION` unset or holding a different subnet than the instance is in (the plan log carries a warning from `terraform/main.nix` when it is unset); the `ami` pin edited without following the replacement procedure; a root volume whose `encrypted` flag does not match (the module defaults it to `true`, and it is ForceNew); or `key_name` changed. Note `disable_api_termination = true` will **not** stop the destroy -- the provider clears protection first. | **Never approve this**, and be aware the deploy workflow applies with `-auto-approve`, so it must not reach `main`. Diff the plan against `aws ec2 describe-instances` on the live instance to find which attribute disagrees, and fix the config or the secret rather than the plan. A genuine AMI change is a blue/green replacement -- see "Replacing the bastion AMI" in [`sops.md`](./sops.md). |
| `MISSING s3://dailp-dev-media-storage/db-backups/...` from the `Upload database backups to S3 from bastion` step | `upload_to_s3.sh` reported success but the object is not retrievable, so the run's verification refused to call the backup good. Either the upload silently failed for one of the two files, or the key differs from what the workflow expected. | Nothing is pruned from the bastion in this state -- the run's `~/backups/db/<timestamp>/` directory is deliberately left in place, so the artifacts still exist. `run-on-bastion -- 'ls -lR /home/ec2-user/backups/db'` to confirm, then re-upload by hand with `upload_to_s3.sh -b=dailp-dev-media-storage -p=db-backups/<timestamp>`. Remember to remove the directory afterwards; the root volume is small (declared as 30 GiB, but check `df -h /home` -- an instance predating that setting, or a volume grown without `growpart`, still has 8 GiB of filesystem). |
| `Uploaded object size does not match the local archive` in the Data Backup workflow | The multipart upload reported success but S3's `ContentLength` is short of the local zip, i.e. the object is truncated. | Do **not** treat that key as a good backup. Re-run the workflow's upload; the key is overwritten in place (the bucket is versioned, so the short object is retained as a non-current version rather than lost). To check an existing object by hand, `aws s3 cp` it down and compare `sha256sum` against the `sha256:` line the `Zip backup bundle` step logs. |
| `No space left on device` during `Generate XML backup bundle` or `Zip backup bundle` | Runner disk, not bastion disk -- the bundle now lives on `/mnt`, and `zip -r` holds the raw tree and the finished archive at once, so peak need is roughly twice the bundle size. | Read the `df -h / /mnt` line the `Prepare bundle workspace` step prints, and the `df -h /mnt` at the end of the zip step, which is the early warning that the *next* run will not fit. If `/mnt` is genuinely too small, the bundle has outgrown a hosted runner and the export needs to stream to S3 rather than stage a zip on disk. |
| Transfer dies partway through a large `scp`, reported as `scp failed after Ns` | Tunnel idle timeout or a dropped session mid-transfer. Note that `scp` connects to the local `session-manager-plugin` socket, not to the bastion, so kernel TCP keepalives are answered locally and cannot see this; only `ServerAlive*` can. The flake apps set `-o ServerAliveInterval=60 -o ServerAliveCountMax=10`, so a dead session surfaces as a failure after ~10 minutes of silence instead of hanging indefinitely. Applies to the interactive `copy-to-bastion` procedures in [`sops.md`](./sops.md) and to the Data Backup workflow's `Copy backup scripts to bastion` step, which still deploys `./scripts` there. The workflow no longer copies the backup *bundle* to the bastion, so a failure here is a tooling-deployment problem and not a lost backup -- check whether the S3 upload step above it succeeded before treating the run as a data loss. | Retry the copy. The progress heartbeat tells you whether it died early or late: `copy-to-bastion` prints `... still copying (Ns elapsed)` every 15s. If it recurs at the same point, suspect disk space on the bastion -- the root volume is small, and the declared size in Terraform is not necessarily the filesystem size -- so check `run-on-bastion -- 'df -h /home'` rather than the tunnel. If it recurs on a genuinely slow link, raise `ServerAliveCountMax` in `flake.nix`. Do not use this path for multi-gigabyte files: SSM port forwarding runs at single-digit MB/s, which is why the backup workflow uploads to S3 from the runner instead. |

## Nothing Above Matches

If you're seeing an error not listed here, capture the full command and its stderr and escalate to
the assistant program manager rather than continuing to retry. Two things are worth checking first,
because they cause most of the confusing cases:

```sh
aws sts get-caller-identity     # are you who you think you are, with unexpired credentials?
echo "$BASTION_ID"              # is the target actually set?
```

Reason from the error text only after those two are known good -- error shape is a much less
reliable signal than identity and configuration.
